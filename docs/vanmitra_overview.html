VanMitra: Community Forest Resource (CFR) Claim Module

An offline-first mobile app that helps a village prepare, file and track its Community Forest Resource claim under Section 3(1)(i) of the Forest Rights Act, 2006, correctly, completely and with every legal deadline visible.

Built in cooperation with a partner NGO and for use alongside government committees. Pilot village: ओझर (Ozhar), Jawhar Taluka, Palghar District, Maharashtra.

Flutter · FastAPI · PostgreSQL + PostGIS Marathi · Hindi · English Works offline for weeks
AWARENESS→CLAIM→VERIFICATION→RESOLUTION→RECOGNITION→RECORD→GOVERNANCE

1. What we are building

A CFR claim is a village asking the government to recognise its right to protect, regenerate, conserve and manage its customary forest. It is not a land-ownership claim, and the title is held by the Gram Sabha. If the claim is rejected, the whole village loses, not one family.

VanMitra IS…

  • A community-side record and preparation tool
  • A checklist that tells the village what is still missing, with the rule cited
  • A generator of the paper documents the law requires (20 G-series documents + Form C)
  • A tracker of legal deadlines (60-day petition windows, 3-month claim window…)
  • A tamper-evident archive of the Gram Sabha's own records

VanMitra is NOT…

  • A government system of record, or an official portal
  • A judge of eligibility, and it never shows a score
  • An approver or rejecter of claims at any level
  • A replacement for signed paper. Paper is the legal record; the app stores its scan
  • A way for anyone to bypass the Gram Sabha
Why this matters: a missing evidence tag, an unrecorded quorum, an unsigned verification sheet or a lost 60-day limitation period can each be enough for a claim to be rejected. The app exists to stop those procedural failures.

8. Technical approach

1 · The law lives in pure functions

FRC composition, quorum, completeness, clocks and the state machine are plain, side-effect-free functions in domain/, 100% unit-tested and citing their rule.

2 · The server is the referee

Every hard block is enforced by the backend. The app mirrors the checks for instant feedback, but if the app is wrong, the server still refuses.

3 · Explicit state machine

No boolean flags. Every transition has a guard, writes a workflow_event, and may start a legal clock. Outcome states change only from uploaded orders.

4 · Offline-first, device as temporary record

UUIDv7 IDs minted on the device, a Hive outbox, idempotent batch sync, chunked resumable uploads. Signed records never merge silently.

5 · Append-only + hash chain

Evidence, meetings, resolutions, orders and events are never updated or deleted. Corrections supersede. One SHA-256 chain per Gram Sabha.

6 · AI is optional and removable

OCR and speech-to-text only add metadata. Switching off the assist/ layer changes nothing in the legal workflow.

7 · Paper out, scan back

Every legal artefact is an HTML template → PDF in Marathi, Hindi and English with a signature block, then the signed scan is hash-sealed.

8 · Contract-first API

The backend publishes OpenAPI with examples before building each stage; the frontend works against a mock and never waits.

9 · Configuration, not code

Officer designations, districts and addresses live in the authority_actor table with validity dates, so transfers don't break history.

Request flow: recording a Gram Sabha resolution

  1. GS Secretary marks attendance in the app → stored in Hive → queued in the outbox (works offline).
  2. On sync, POST /meetings/{id}/attendance → the server computes the 3 quorum tests and stores the numbers on the meeting.
  3. Secretary records the resolution → POST /meetings/{id}/resolutions.
  4. Server guard: quorum passed? If not → 409 {rule: "Rule 4(2)"}, and the app explains which test failed.
  5. If yes: resolution row appended with record_hash = SHA256(payload ‖ prev_hash); boundary frozen as GS_APPROVED; workflow_event GS_READY → GS_RESOLVED; 60-day petition clock started.
  6. G12 + G13 PDFs rendered in the background → printed → signed → scan uploaded and sealed.

12. Data model

🔗 = append-only and hash-chained. UPDATE/DELETE are blocked at the database; corrections are new rows with supersedes_id.

Village & people

  • village: LGD, GP, taluka, district, parent_village_id, consolidation status
  • gram_sabha: chain head hash
  • gs_member: gender, ST/OTFD category, is_claimant
  • frc, frc_member: composition proof, chair/secretary
  • app_user, user_role: role × village, validity

Case & evidence

  • case: claim_type (CFR / IFR / CR), state, ack serial, window dates
  • case_claimant
  • evidence 🔗: rule_ref, kind, media, source, is_substitutable, verified_by
  • elder_statement: audio, transcript, signed scan
  • media: sha256, gps, accuracy

Geography

  • cfr_boundary: versioned Polygon (4326), source, status, area (UTM), sealed hash
  • boundary_segment, landmark, use_zone
  • boundary_walk: named elders, trace
  • adjacency, dispute: overlap geometry, joint meeting, referral

Verification & Gram Sabha

  • verification_proceeding 🔗: forest/revenue signed or absence, attempt no.
  • recusal
  • gs_meeting 🔗: counts + stored quorum result
  • attendance: manual / face
  • resolution 🔗: number, trilingual text, votes, boundary link

Authorities & workflow

  • authority_actor: office, designation, jurisdiction, validity
  • authority_order 🔗: kind, order date, communicated_on, reasons_given, grounds
  • workflow_event 🔗: from → to, actor, order, reason, due date
  • legal_clock: kind, due, extension, alerts sent

Output & governance

  • correspondence: letter, addressee, dispatch, reminder
  • generated_document: template, language, signed scan
  • consent: purpose, given/withdrawn, oral/written
  • audit_log: actor, action, object, purpose
record_hash(n) = SHA256( canonical_json(payload(n)) || record_hash(n-1) )
Chained tables : evidence · verification_proceeding · gs_meeting · resolution · authority_order · workflow_event
Chain scope    : one chain per Gram Sabha (a village can verify its own history)
Anchoring      : chain head printed weekly in the Gram Sabha register (offline anchor)
Correction     : never an update. A new row supersedes the old one and records why

14. Rule engines

FRC composition [Rule 3(1)]

10 <= n <= 15
if any ST: st >= ceil(2n/3)
women >= ceil(n/3)

Returns which test failed and by how much.

Quorum [Rule 4(2)]

t1 = present   >= ceil(members/2)
t2 = women     >= ceil(present/3)
t3 = claimants >= ceil(total/2)
pass = t1 and t2 and t3

Inputs + result stored on the meeting, never recomputed.

Documentation completeness

C-1 ≥2 verified 13(1)
C-2 ≥1 verified 13(2)
C-3 boundary GS-approved
C-4 landmark per segment
C-5 forest & revenue signed/absent
C-6 elder statement OR ≥3 13(1)
C-7 quorum passed
C-8 neighbours intimated
C-9 acknowledgement issued
C-10 no unresolved overlap

Output: "8 of 10" + named gaps. Never a score. Geo items never count alone.

RuleWhy
UUIDv7 IDs minted on the deviceRecords created in the field are referenceable before reaching the server; time-ordered IDs keep the outbox in causal order
Append-only ledgers never mergeTwo devices adding evidence to the same case both succeed; nothing to reconcile

Ground rules

  • main is protected. No direct pushes; one review per PR
  • Branches: be/…, fe/…, docs/…
  • Commits: feat: fix: docs: test: refactor: chore:
  • API changes go to OpenAPI first, in an api-change PR
  • Never commit secrets, google-services.json, .env or machine paths

Definition of done

  • Traces to a stage and a rule (or labelled facilitation)
  • Breaks none of the 10 rules (no scores, no decisions)
  • Tests added; CI green
  • All text in mr / hi / en
  • Works offline, if it is a field action
